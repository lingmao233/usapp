# 热量模块修复与增强计划

## 根因速览（已取证）

1. **红茶→火腿震荡**：`calorie_name_corrections` 表（`server/app/db/database.py:281`）记录了 `红茶→火腿`，`_apply_name_correction`（`server/app/services/ledger.py:566-573`，调用点 :343）每次识别都精确匹配无条件改写；你 3 次「改回来」只是新增反向行，原行未删，形成双向震荡。库里现存 4 行脏数据（红茶→火腿、火腿→茶、火腿→红茶×2）。
2. **红茶 50g=147 卡**：联网兜底 `web_search_food("红茶")` 返回错误值 294 kcal/100g（疑似 kJ/kcal 混淆），仅过 `0<x≤1000` 检查（`server/app/ai/__init__.py:497-498`）就落全局 staging 表且 `verified=1`；294×50/100=147。与火腿无关（50g 火腿≈150 卡纯属巧合）。
3. **更新估值 10 分钟只提示一个**：前端无轮询（`Calories.tsx` 的 `load()` 仅挂载/切日/操作后触发）；提示只挂 `source=model` 且有 grams 的条目（`ledger.py:882`）；联网回填 20-25s/个且失败静默；staging 按 name+brand 精确匹配，改名后断链。
4. **删除/历史功能已存在**（`DELETE /api/calories/{id}` `api/ledger.py:128`、日期切换 `Calories.tsx:690-700`），线上旧版未部署而已。

## Phase 0：脏数据一次性清理脚本

新建 `server/scripts/cleanup_pollution.py`（可复用、幂等、默认 dry-run，`--apply` 才执行）：
- 删除 `calorie_name_corrections` 中红茶↔火腿 4 行循环数据（通式：删除互为反向的纠正对）
- 删除 `food_nutrition_staging` 中 `红茶=294` 行（id=3），级联清掉 `food_staging_approvals` 引用（注意 BUG-020 的 FK 教训）
- 报告（不自动改）受污染的已入账条目（如 `calorie_entries` a5b4fb1c4a37 红茶147kcal），输出清单供你决定删/改
- 本地 `server/data/app.db` 先跑一遍验证，生产部署后再跑一遍

## Phase 1：名字纠正防震荡（`server/app/services/ledger.py`）

- 识别时 items JSON 增加 `raw_name` 字段（视觉模型原始输出，纠正应用前保存，`ledger.py:339-343` 处）
- `update_calorie_item`（`ledger.py:598-707`）改名 cur→new 时：
  1. 若 `new == raw_name`（改回原识别名）→ **删除** `(recognized=raw_name, corrected=cur)` 行，不插入新行
  2. 否则插入 `(cur→new)` 前做防环：沿 new 的纠正链走 ≤5 步，若能回到 cur 则先断链再插入
  3. 同时删除 `(recognized=new, corrected=cur)` 的既有行，杜绝双向震荡
- `_apply_name_correction` 不变（最新一条生效语义保留）

## Phase 2：web 值交叉校验 + 品类先验

- `backfill_food_web` 的 `missed` 结构从 `(name, brand)` 扩为 `(name, brand, model_per_100g)`——识别处已有 `model_kcal` 与 `grams`（`ledger.py:350,346`）可算出模型隐含单价；grams=0 时传 None
- 落库前（`ai/__init__.py` 返回处或 staging upsert 处统一收口）：
  - **交叉校验**：web 值与 model_per_100g 偏差 >10 倍 → 拒绝落库，任务记录里注明原因（不再静默 verified）
  - **品类先验**：名称命中饮品类词表（茶/水/咖啡/可乐/汽水/果汁/汤等，注意「奶茶」除外可放宽）且 web 值 >80 kcal/100g → 拒绝落库
  - 可选增强：web 值 ≈ 模型估值 × 4.184（±20%）时判定为 kJ 误报，除以 4.184 后再过上述校验
- 改名路径的同步联网入库（`ledger.py:636-649`）走同一校验函数

## Phase 3：SSE 推送估值更新提示

- 后端 `GET /api/calories/events?account_id=`（`api/ledger.py` 新增）：FastAPI 原生 `StreamingResponse(text/event-stream)`，无新依赖（符合白名单）
  - 进程内简单事件分发：`backfill_food_web` 每完成一个菜名入库成功后 notify 该账号的订阅队列；SSE 端点 await 队列推事件 `{"type":"staging_ready","name":...}`，30s 心跳保活；断线由 EventSource 自动重连
- 前端 `Calories.tsx`：挂载时 `new EventSource`，收到事件调 `load()` 刷新（upgrade 按钮自然出现），卸载时关闭；`src/core/api.ts` 加事件 URL 帮助函数

## Phase 4：staging 完整管理后台

- 后端 `server/app/api/nutrition.py` 新增：
  - `GET /api/nutrition/staging?query=&page=`：列表+搜索（名称/单价/brand/来源/verified/认可数）
  - `PATCH /api/nutrition/staging/{id}`：改 name/brand/kcal_per_100g
  - `DELETE /api/nutrition/staging/{id}`：软删（加 `deleted` 列 + `updated_by/updated_at` 审计字段，`database.py` DDL 增列，注意老库 ALTER 迁移）
  - `POST /api/nutrition/staging`：手动新增正确行（治理「红茶」时可直接补 2 kcal/100g）
  - verified 标记切换
  - 权限沿用共建思路：所有账号可操作，记录操作者；删除 approvals 引用一并处理
- 前端：热量页「我的识别纠正记录」面板（`Calories.tsx:20-91` 同款风格）旁加「共建食物库」面板：搜索/列表/改值/删除/新增
