# 个人功能设计：目标 / 每日计划 / 记账 / 热量

> 2026-08 定稿。四个个人维度新功能的完整设计，由 12 轮拷问逐分支敲定。
> 与圈子社交体系的关系、GitHub 调研结论、分期范围均在文内。

## 0. 一句话定位

在熟人小圈子社交 App 内新增**账号级个人工具层**：每日计划、目标系统（减肥/存款/学习）、拍照记账、拍照热量估算。数据个人所有，可选公开到指定圈子接受熟人"鞭策"。与圈子功能正交，不动现有 17 张表的可见性逻辑。

## 1. 归属与可见性

- **归属维度：账号级（user_id），跨圈子一份。** 减肥目标、账本、热量记录与圈子无关，加几个圈子都只有一份。
- **默认私有。** 公开是逐目标的显式动作，两个旋钮：
  - **受众**：指定自己所在的若干圈子可见；没选的圈子永远看不到，不做"所有同圈人可见"。
  - **粒度**：用户自选「进度摘要」（百分比、连续天数、今日完成 x/y）或「含明细」（账单金额、体重、具体热量）。
- **过滤永远在服务端**，沿用现有隐私铁律的实现模式。
- **记忆归属**：蒸馏管线新增"消费习惯"维度（餐饮/出行等类目的日均花费区间），账号级私有，**不进圈子维度的 `user_profiles`**。

## 2. 鞭策（nudge）

熟人监督是唯一的社会化出口，规则全部钉死：

- **纯手动**，系统绝不自动催促；只有圈友能发起。
- 目标公开后，圈友在其进度页看到"鞭策"按钮（当天计划未全部完成或目标逾期时点亮）。
- **限频：同一用户对同一目标所有者一天 1 次**（对人不对目标）。
- **内容：自由留言**；独立 `nudges` 表，不进现有评论体系。
- 通知走现有 Web Push（pywebpush）+ 应用内未读。
- **反制**：目标所有者可按目标关闭鞭策、可按人屏蔽；目标转回私有后鞭策入口消失。

## 3. 目标系统

### 3.1 类型化模板（一期三类）

| 类型 | 问卷字段（全部可跳过） | 联动 |
|---|---|---|
| 减肥 | 当前体重、目标体重、目标日期、身高、年龄、性别、作息、运动基础 | 热量计算 + 每日计划（摄入预算/运动安排） |
| 存款 | 目标总额、截止日期、固定收入（可选）、固定支出（可选） | 记账 |
| 学习 | 学什么、目标日期、每日可投入时长、当前水平 | 计划打勾率 |

- **自定义目标**保留：`type=custom`，一期只享 AI 生成计划，字段预留后续由 AI 归类到已有类型以继承联动。
- 问卷可全部跳过：跳过则用通用默认值生成计划并标注"按通用值估算"。
- 不收集病史、经期、饮食禁忌——不碰医疗建议。

### 3.2 关键公式（全部规则计算，不经 AI）

- **BMR（Mifflin-St Jeor）**：男 = 10×体重 + 6.25×身高 − 5×年龄 + 5；女末项 −161（kg/cm/岁，kcal/天）。乘活动系数得每日消耗，减肥缺口分摊得**每日热量预算**。
- **存款月预算**：固定收入 − 固定支出 − 弹性花销基线（蒸馏出的习惯区间）→ 每月建议存款额。
- **MET 换算**：热量 = MET × 体重 × 小时。内嵌跑步/快走/骑车/游泳等十余项 MET 常量表（来源见 §9）。

## 4. 每日计划

- **单一今日清单**，AI 生成条目与用户自定义条目混排，条目级标注来源。
- **两层生成**：
  1. **周期框架（设目标时）**：确定性规则算（热量预算、每周运动次数、月预算），不调用 AI。
  2. **当日计划（懒生成）**：当天首次打开时由 DeepSeek 生成，输入必带**昨日完成情况 + 剩余目标进度**，自适应调整是默认行为。沿用周报懒触发 + 缓存模式。
- 条目一律可编辑、可删除、可手动打勾；AI 条目无特殊地位。
- **无目标也可用**：纯自定义条目不需要设目标。
- 条目抽象参考 Habitica 三分法（习惯/每日任务/待办）与 super-productivity 的顺延思路（见 §9）。

## 5. 记账

- **识别管线**：小票/支付截图/账单截图 → 豆包视觉 LLM 端到端一次调用 → 结构化 JSON 数组（金额/商户/时间/收支/分类，**支持一图多笔**）。不接专门 OCR API。
- **确认流（强制）**：识别结果进"待确认"卡片，默认全填好，用户确认或修改后入账；未确认不进账本。
- **分类**：一期预设 8-10 个类目，AI 映射 + 用户可改（自由分类名会让统计报表没法做）。
- **手动记账**：简单表单（金额/分类/备注/时间），现金场景兜底，也是未配视觉模型时的降级路径。
- 分层策略"规则优先、AI 兜底"（商户→分类映射先查规则表），省 token。

## 6. 热量计算

- **管线（识别与计算拆开）**：食物照片 → 视觉模型认菜名 + 估分量（grams）→ 查表计算每项热量与总量；拍照时可补一句文字描述（"红烧肉一碗约 300g"）显著提升准确度。**速度设计（2026-08-21，5s 目标）**：识别走 800px 识别副本 + food 档默认 off（快档，~2.5s）；模型自报包装食品但没读出品牌时自动带思考重试一次（两级策略——实测 off 漏三养品牌、on 认出，1.8s vs 14.9s）；查表全不中的菜名不再同步联网，本次按模型估值标 `model` 立即返回，联网结果由后台任务写入共建库（与用户是否确认入账解耦，估值被丢弃也照入）；视觉调用统一 temperature=0 压采样抖动。
- **查表计算**：内嵌《中国食物成分表》数据（Sanotsu/china-food-composition-data 清洗 vendor 进 `server/scripts/assets/food_nutrition.json`，启动时幂等灌入 `food_nutrition` 表）。菜名匹配先 LIKE 归一（去括号备注互含；**单字查询不做互含扩展**——护栏：否则「茶」会吸到「茶肠」；查询带高油做法时含同类做法信息的行优先——煎荷包蛋→荷包蛋（油煎），且**命中行无做法信息时拒收**——炒鸡蛋绝不按煮鸡蛋计价，让给联网拿做法级单价），不中再走 name 向量余弦（阈值 0.75），再不中剥词首做法词降级匹配通称行（清炒时蔬→时蔬；卤/酱/拌等品类字不剥）；命中则 kcal = kcal_per_100g × grams / 100（item 标 `source="table"`），未命中回退模型估值（`source="model"`）。识别 prompt 要求菜名带做法（炒鸡蛋/荷包蛋而非鸡蛋）。**联网兜底通道分流**：树洞配置为 Kimi 系（moonshot/kimi.com）时走 `$web_search` 真联网（阿里 enable_search 写法在 Kimi 端点会被静默忽略，假联网）；其他厂商仍走 LLM_* + enable_search。
- **运动等效**：MET 公式按问卷体重（缺省 65kg 并标注）换算跑步/快走/骑车/游泳四种时长，规则计算。
- **确认流**：与记账同一交互模式，数字可改后入账；支持纯手动录入（数字 + 备注）。
- **改克数（2026-08-20 增）**：pending 待确认卡与已入账记录都可逐项改克数（`PUT /api/calories/{id}/items`）；识别时 item 落 `kcal_per_100g` 单价，改克数按它重算（模型估值项无单价则线性缩放），total/运动等效/超预算联动同步。
- **克数纠正校准（在线校准，非模型微调）**：改克数且与原估值不同时落 `calorie_gram_corrections`（菜名/AI 原估/用户修正）；下次拍照识别时把该账号最近 8 条纠正（同名取最新）注入 FOOD_PROMPT 的 calibration 块，让分量估计越来越贴合这个用户的真实分量。隐私铁律：只用本账号的纠正，不跨账号。
- **图片型 RAG（2026-08-21 增，以图搜图）**：确认入账时把识别图（800px 副本）经多模态 embedding（doubao-embedding-vision，走 `/embeddings/multimodal` 子路径——套餐网关的主路径只收文本）向量化入 `calorie_food_images`（账号级，隐私铁律不跨账号）；再识别单菜品照片时先以图搜图，余弦 top1 ≥ 0.9（实测同图 ≈0.999、不同食物 ≈0.42、食物vs人像 ≈0.23）即复用历史确认的菜名/品牌/单价（标 `image_rag`），克数仍按新图估——同物同价，识别抖动归零；未命中走常管线。
- **改菜名（2026-08-20 增；2026-08-22 防震荡）**：同一端点可改识别错的菜名——记名字纠正（`calorie_name_corrections`：识别名→纠正名，下次识别同名直接生效），再重走匹配链：查表/共建库命中按新单价×克数重算；不中且联网开时联网搜（过 `sanitize_web_value` 清洗，见下）、搜到写入 staging（`web_pending` 待认可）；全不中保留当前热量标 `model`。防震荡（BUG-021）：item 留底 `raw_name`（模型原始输出/最早录入名）；改回 raw_name = 撤销纠正（删正向行、不插反向行）；其他改名先删反向行再插——任何时刻一个名字对只有一个纠正方向。
- **手动录入即时匹配（2026-08-20 增）**：热量非必填——输食物名防抖调 `GET /api/calories/lookup`（只读查正式表+共建库），命中且填了克数就自动算好热量填入（可再改），未命中提示手填或收录共建库；带明细的手动录入（`add_calorie` 支持 items）之后同样可逐项改克数/改名。
- **估值钳制与升级提示（2026-08-21 增）**：模型估值设物理上限（隐含单价 > 1000 kcal/100g 必估飞，钳回上限）；prompt 要求估值按生活常识给量级（无糖茶/黑咖啡接近 0）且图中食物宁多勿漏逐项扫描。联网后台入库后，已入账的估值条目在今日记录里挂 `upgrade` 提示（"↻ 联网数据：更新为 X kcal"），用户点击才同名重匹配按新单价重算。
- **联网值清洗 + SSE 推送 + staging 治理（2026-08-22 增，BUG-022/023）**：联网值入库前过 `nutrition.sanitize_web_value`——饮品品类先验（名字以茶/水/汁/汤/咖啡等结尾且超上限【饮品 80、奶茶类 150 kcal/100g】即拒绝）+ kJ 误报折算（≈模型隐含单价 × 4.184 判为单位误报，折算后再过先验）；后台入库成功经进程内 SSE 总线（`services/events.py`，30s 心跳）向该账号在线页面推 `staging_ready`，前端 `EventSource(/api/calories/events)` 收到即刷新——升级提示约半分钟内**自动**出现。staging 全局共享错值可治理：`GET/PATCH/DELETE /api/nutrition/staging`（软删+审计，匹配/回填/认可即刻跳过，再添加同名以新值复活），前端「共建食物库管理」面板。
- **克数两步推理与在线校准（2026-08-22 增）**：裸猜克数是视觉模型弱项，FOOD_PROMPT 给参照系把弱项变乘法——第一步认容器估比例（小饭碗 200ml/家常碗 300ml/纸杯 180ml/餐盘摊平 300ml…），第二步乘品类密度（熟饭面 0.6、液体 1.0、肉豆腐 1.05、叶菜 0.3、薯条 0.15、坚果 0.6、糕点 0.4 g/ml）。模型每项自报 confidence（0-1）落 item，前端对 <0.5 的项标「没把握」把人工确认引导到最需要处。校准两层：同类纠正样例（原有）+ 用户级系统偏置 `_gram_bias`（历史纠正 用户实际/模型估计 的中位比值，样本 ≥3、中位偏离 ±50% 视为数据不可信不注入），偏置帮所有食物、样例只帮同类。
- **成分表方括号别名与双向单字护栏（2026-08-22 增）**：《中国食物成分表》把别名写在 `[]` 里（马铃薯[土豆、洋芋]、番茄[西红柿]），normalize 剥括号后 LIKE 永远看不到——现在方括号别名（含厂商半角开全角关的破损括号）与主名同级参与匹配，别名精确命中同 rank 0；单字护栏双向化：查询与候选键任一不足两字不做互含（查询侧防「茶→茶肠」，键侧防「小西红柿→柿」实测 196% 误差）。做法词表补 拍/蒜蓉/清炖（拍黄瓜→黄瓜）。行为数字验收：`scripts/eval_food.py` 匹配层 want 3/11 → 8/11。
- **免责标注**：UI 明示"估算仅供参考"（论文级模型误差 17-22%，商用 App 170-280kcal/餐，别承诺精度）。

## 7. 联动规则（纯确定性，零额外 AI 调用）

### 7.1 减肥 ↔ 热量

- 每笔热量入账即对比 **今日累计 vs 今日预算**（不分摊到每餐）。
- **超了** → 今日清单追加"热量调整"条目（醒目样式）：剩余晚餐预算 + 运动补偿换算，规则生成；**已有条目一律不动**（不整盘重排）。
- **没超** → 什么都不发生。
- 次日计划懒生成时自带"昨日超支"上下文，自动收紧。闭环成立。

### 7.2 存款 ↔ 记账

- **口径=月预算**（不做日预算：花销脉冲式，日预算全是误报）。
- 每笔账入账更新"本月已花/月预算"进度，体现在每日计划顶部与记账页。
- **月底结算卡**：目标存 X、推算实际存 Y（= 固定收入 + 账本额外收入 − 账本总支出）、差额 Z → **滚雪球分摊进剩余月份重算**。用户可手动修正 Y（账本外花销），以修正值为准重算。
- **未填固定收支** → 只给静态"每月建议存 X"，无动态联动。
- 月度建议文案由 DeepSeek 说成人话，数字全部规则算。

### 7.3 学习 ↔ 计划

- 输入=计划条目打勾率；昨日学习条目未完成 → 今日生成时补足（分摊欠账时长）。一期不做专属打卡入口。

## 8. 前端

- **底部 Tab 双入口：「圈子」/「我的」**（圈内顶部导航不动）。
- **「我的」页**自上而下：今日计划卡（完成 x/y + 打卡）→ 进行中目标卡（进度条，点开=目标详情：进度+计划+鞭策入口）→ 工具入口（记一笔/拍热量）。
- 记账/热量不做独立 Tab；同时从计划相关条目直达（点"今日摄入预算"跳热量记录）。
- **一期不做功能开关**：空状态即引导，臃肿靠信息架构压住。
- 前端先按此结构落地，样式细节后续迭代。

## 9. GitHub 调研结论（2026-08）

**直接抄数据/公式（内嵌常量，零运行时依赖）**：
- MET 表：[Compendium of Physical Activities](https://pacompendium.com/)（[CSV 清洗版](https://github.com/andyreagan/compendium-of-physical-activity)）
- Mifflin-St Jeor BMR 公式（公开）
- 中国食物成分表 JSON：[Sanotsu/china-food-composition-data](https://github.com/Sanotsu/china-food-composition-data)（320★）

**抄设计/prompt**：
- [autocoin](https://github.com/hnkjdaxzzq/autocoin)：FastAPI+SQLite+多模态 LLM，账单截图→VLM→JSON 的 prompt/schema 直接可借鉴
- "规则优先、AI 兜底"分层：[FlashBill](https://github.com/Macr0phag3/FlashBill)；中文支付场景分类体系：[AutoAccounting](https://github.com/AutoAccountingOrg/AutoAccounting)
- "图+一句文字描述"提准：CaLoRAify（arXiv 2412.09936）
- 计划条目三分法 [Habitica](https://github.com/HabitRPG/habitica)、顺延 [super-productivity](https://github.com/super-productivity/super-productivity)、目标→拆解→执行→重排闭环 [babyagi](https://github.com/yoheinakajima/babyagi)

**必须自己写**：VLM 识别层、自适应计划闭环、目标规则引擎——业务深度耦合，纯 Python 规则函数 + mock 可测。

**精度预期校准**：[Nutrition5k](https://github.com/google-research-datasets/Nutrition5k)——单图热量估算本质是估算，"给区间+可修改+免责"是正确且唯一的产品姿势。

## 10. 降级与测试

- 未配 `DOUBAO_VISION_MODEL`：记账/热量功能可用，拍照入口提示"请手动录入"，手动表单兜底。
- 全部新 AI 调用走统一抽象层 + mock 桩 + degraded 落库：
  - DeepSeek：当日计划生成（懒触发 ≤1 次/人/天）、月度存款建议文案
  - 豆包视觉：账单识别、食物识别（各配确定性 mock 数据）
- 测试强制 mock 模式，**规则引擎测死**：热量对比与调整条目、存款滚雪球重算、鞭策限频与屏蔽、目标可见性过滤（沿用现有服务端过滤测试模式）；AI 层只测 mock 接线。
- 硬约束不变：零新依赖；`weapp/` 冻结不动；`src/core/` 改动保持 weapp 编译通过。

## 11. 分期建议

- **一期**：目标三类型 + 问卷、每日计划两层生成、记账（VLM 识别 + 确认 + 手动）、热量（VLM + 成分表 + MET + 确认 + 手动）、减肥/存款/学习三条联动规则、可见性体系、鞭策、「我的」Tab。
- **二期候选**：自定义目标的 AI 类型归类、按人屏蔽列表 UI、分享卡片（主动晒明细）、学习专属打卡/计时、更多目标类型。
