## 2. 专题一：热量识别——如何在保证准确率的前提下缩短时间

### 2.1 起点（改造前有多慢）

- 未命中菜名**同步**联网查询，假通道 60s read timeout 后才回模型估值（BUG-019）
- 思考档全开做精细识别：单次 14.9s（BUG-019 实测）
- 原图直传（1600px+），base64 载荷大

### 2.2 提速手段全景（每条：怎么做 → 提速多少 → 为什么准确率不降反升）

| # | 手段 | 时间收益 | 准确率保障 |
|---|---|---|---|
| 1 | **两级识别策略**：默认思考 off 快出（实测 **1.8s**）；只有模型自报「包装食品但没读出品牌」才带思考重试一次（14.9s） | 常规餐 8 倍提速 | 按需付延迟：读包装小字这种精细活才花思考的钱；重试结果完整替换 |
| 2 | **识别副本降载**：上传即产 800px `_s.jpg`，识别用副本、展示用 1600px | 传输与编码时间 | 分辨率对菜名/分量识别足够（实测两级策略下品牌识别正常） |
| 3 | **temperature=0** 统一识别类调用 | 消除采样抖动的重试 | 同图同结果，可回归、可评测 |
| 4 | **联网移出热路径**：未命中菜名先按模型估值返回，后台 `backfill_food_web` 入库（线程池 3 并发+任务层重试） | 首屏不等 20-25s 联网 | 下次识别同食物直接命中 staging；本次已有模型估值兜底 |
| 5 | **SSE 推送升级提示**：入库完成即推 `staging_ready`，前端自动刷新（BUG-023 修复） | 用户零等待感知 | 联网值先过清洗（§3）才提示 |
| 6 | **图片型 RAG（以图搜图）**：单菜品照片与历史确认图余弦 top1≥0.9 直接复用菜名/品牌/单价 | 免一次完整识别链 | 实测同图 ≈0.999、不同食物 ≈0.42、食物vs人像 ≈0.23——阈值分离度大；同物同价，识别抖动归零 |
| 7 | **在线校准（克数纠正注入）**：用户改过的克数作为样例注入 prompt，越用越贴合本人 | 长期减少人工修正轮 | 校准只影响本人；与画面冲突时以画面为准 |

### 2.3 准确率不降反升的证据

匹配层评测（`eval_food.py`，30 用例，参照值钉在《中国食物成分表》真实行）：

| 指标 | 基线 | 改后 |
|---|---|---|
| must（基本盘命中率） | 19/19 | 19/19（提速无回退） |
| **want（改进位）** | **3/11** | **8/11** |
| 土豆/洋芋/红薯/小西红柿 | miss / **196% 误差**（吸中单字行「柿」） | **全部 0% 误差** |
| 西红柿 | 靠厂商破损括号运气命中 | 正规别名路径 0% 误差 |

克数侧（误差最大头）的准确率手段：
- **两步推理 prompt**：估克数（视觉弱项）→「认容器估比例（碗 200/300ml…）× 品类密度（熟饭面 0.6/液体 1.0/叶菜 0.3 g/ml）」的乘法
- **confidence 自报**：每项 0-1 把握度，<0.5 前端标「没把握」，人工确认引导到最需要处
- **用户级偏置 `_gram_bias`**：历史纠正「用户实际/模型估计」中位比值注入（样本 ≥3、中位偏离 ±50% 判数据不可信不注入、<5% 视噪声）——系统偏置帮所有食物

## 3. 专题二：数据准确性保障体系（多道防线）

### 3.1 计算链：识别与计算分离 + 五级降级

模型只认菜名+估克数，热量一律查《中国食物成分表》（kcal_per_100g × grams/100）：

```
LIKE 归一互含（含方括号别名）→ 文本向量余弦 ≥0.75 → 剥做法词降级
→ 共建 staging → 模型估值（钳制 ≤1000 kcal/100g）
```

护栏：
- **单字护栏双向**：查询侧防「茶→茶肠」（BUG-019），候选侧防「小西红柿→柿」（196% 误差实测）
- **高油做法守卫**：炒鸡蛋绝不按煮鸡蛋计价，宁 miss 走联网拿做法级单价
- **品牌优先分组**：识别出品牌 → 品牌行 > 通用行 > 其他品牌行

### 3.2 联网数据：三道闸 + 治理闭环（红茶 294 案例复盘）

**发现**：红茶 50g 算出 147 kcal（红茶本身 1-4 kcal/100g）。
**止血**：取证定位 staging id=3 红茶=294（联网把干茶叶值当饮品）→ `cleanup_pollution.py` 清理（精准命中、幂等）。
**根治**：
1. **源头（prompt）**：形态必须一致（按吃进去的形态，点名红茶案例）/ 单位 kcal（kJ÷4.184、「每份」→每 100）/ 与视觉估值交叉自检（差 10 倍先怀疑自己）
2. **入库前（sanitize）**：饮品品类先验（茶/水/汁/汤结尾 >80 拒、奶茶类放宽 150）+ kJ 折算（837→200 实测用例）
3. **入库后（治理）**：staging 管理面板（查/改值/软删+审计），软删即刻退出匹配
**防复发**：有证据的设计取舍——对称「差 10 倍即拒」实测误伤正确值（能量棒模型估 1/联网 250 正确），降级为 kJ 折算参照，拒绝判定交给品类先验。

### 3.3 信任管线（用户共建数据）

- 手动添加 → 后台联网核验，差 ≤50% 才 verified=1；查表未命中联网值 → 落库即 verified 但 item 标「待认可」由用户点击升级
- **3 个不同账号认可 → 晋升正式成分表**（同人同物去重计数）
- 认可计数迁移的外键坑有专项自愈（BUG-020）

### 3.4 评测闭环

`eval_food.py`：must ≥95% 才退出码 0（可挂 CI）+ 历史 jsonl 趋势 + 端到端框架
（厨房秤标注照片 → 名字准确率/克数 MAE/热量 MAE，格式示例已备）。

## 4. 专题三：树洞（Agent + 记忆层）

### 4.1 提速与可靠性（当日改造，数据见 §0）

| 轮次 | 改前串行 LLM 调用 | 改后 | 手段 |
|---|---|---|---|
| 纯倾诉（最常见） | 5 次 | **2 次** | route+查询改写合并一次 JSON 调用；倾诉轮结构性跳过工具节点（原为空转） |
| 自伤危机轮 | 3 次（含 120s 生成后丢弃） | **0 次** | 护栏前置到路由节点 + 条件边直达写回 |
| 任何轮的厂商抖动 | 整轮 500（白等 2 分钟） | 降级续跑 | 路由挂→默认倾诉；工具挂→无工具；仅生成挂才 502 |

### 4.2 能力补齐

- **流式输出**：SSE 解析器纯类离线单测；与 $web_search 回声协议共存（工具轮过渡叙述不外发）；`delta*→done` 事件序，done 带权威整包对齐展示与落库；前端无 delta 即挂自动回退整包
- **思考程度**（用户可调）：页头三档「快/平衡/深思」随人设卡持久化；跨厂商思考参数收敛为共享模块 `ai/reasoning.py`（vision/llm 同源）；400 剥参重试自愈（真 httpx.Response 构造的 400→200 用例）
- **「我吃了什么」**：`query_calories` 回菜名明细（跨餐去重、截断、无明细回退备注）+ day 参数
- **可观测性**：每轮落 task_runs（treehole_chat/l2_refresh：状态/延迟/降级）

### 4.3 记忆层 L0-L3 与修复

| 层 | 职责 | 写入 | 消费 |
|---|---|---|---|
| L0 原文 | 一字不差存档，永不压缩 | 每轮同步 | 最近 20 条进 prompt；history |
| L1 原子 | 一条一事实（偏好/事实/事件/承诺） | 每轮 langmem 抽取 | 检索池一路；prompt top5 |
| L2 场景 | 原子聚成话题 | 响应后后台 | 置顶主题常驻注入 |
| L3 画像 | 跨圈长期画像 | 每晚蒸馏 | prompt 画像块；记忆工具 |

**BUG-024**：langmem 的 ChatOpenAI 温度写死 0 被 k3 全量 400——**L1 从上线起一次都没
写进去过**（对话正常是降级兜住）。修复为温度单点解析 `resolve_temperature()`，两侧
共用；回归用例钉「两侧一致」（=1 与默认 0.7）。

## 5. 专题四：其他功能域优化（历史提交 + BUG 全录）

### 5.1 愿望与共同愿望（秒回与空窗治理）
- **加愿望秒回**（BUG-003）：同步串行 AI（分类+向量各数秒）→ 校验即入库返回，分类/向量化后台管线补齐——对齐碎片墙的既有范式
- **共同愿望 SWR**（BUG-008）：指纹未命中同步重算（60s+ 空窗）→ **stale-while-revalidate**：先回旧结果+refreshing 标记（120s 防抖），后台重算，前端 3s 轮询收敛换新
- **匹配池语义**（BUG-004）：生成方案不再把愿望踢出匹配池；「完成」改为用户勾选（可逆），done 才出池
- **超时治理**：匹配 LLM 超时 60→120s 显式可配

### 5.2 方案生成（类型人格体系，BUG-007）
- 愿望分析升级为枚举分类（出行/学习/聚餐/活动/约人/倾诉）+ `need_real_data` 判断——约人/倾诉**强制不查高德**（人名当店名搜地图的根治）
- 每类型**服务端写死实现路径要点**，LLM 只选类型不许发明路径；无真实数据时严禁把愿望原文词当店名
- 消极情绪双形态：换树洞人设先接住情绪不玩梗

### 5.3 周报与外部数据
- 周报 prompt 分区（BUG-005）：写作纪律标明「绝不要写进报告」，杜绝内部规则被渲染成章节
- 高德数字签名（BUG-006）：新政后不带 sig 静默失效 → 按 key 升序 MD5 实现签名，已知答案向量锁定算法
- 事实纪律：方案/周报严格区分「查到的真实数据」与「经验建议」

### 5.4 记忆与向量基础
- 维度守卫 + 全表回填（BUG-002）：cosine 维度不一致按不相似处理（一处修复覆盖四条链路），reembed 扩到 wishes/knowledge
- 蒸馏事务边界（BUG-001）：写锁从 80s 缩到毫秒级（逐行提交，幂等可续跑）+ busy_timeout 30s

### 5.5 前端体验
- IME 回车守卫（BUG-009，项目规约级）、剪贴板双通道 copyText（010）、375px 宽度核算制度（012）、路由条件挂载与导航分离（013，jsdom 真实产物回归 9 断言）
- 热量页：日期日历 + 回到今天 + 删除按钮加重 + 待确认卡丢弃真删 + 纠正记录面板（曾写而未挂载）
- 树洞页：流式气泡、思考程度选择器、人设卡双模式（模板/整段粘贴）

### 5.6 部署与启动
- Windows 开发环境兜底（011）；部署脚本 awk 化（014，6 场景最坏输入测试）
- 灌库批量+容错（015：embed_texts 批量、失败跳过不阻塞启动、空表自动重试；火山 input 上限 10 分块适配——016）
- 厂商参数自愈体系（016/018/024）：温度可配、思考档 400 剥参重试、「未配置」与「调用失败」分流
