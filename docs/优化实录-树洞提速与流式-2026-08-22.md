# 优化实录：树洞提速 + 降级 + 护栏前置 + 流式（2026-08-22）

> 盘点结论（见 `优化清单-2026-08-22.md` 树洞节）：树洞的三个结构性问题是**慢**（每轮
> 最少 5 次串行 LLM 调用）、**脆**（任何一步超时整轮 500）、**黑**（零可观测性记录）。
> 本轮四件事按证据落地，全部有回归测试与评测基线验收。零新依赖（SSE 用 FastAPI
> 原生 StreamingResponse，复用热量轮建好的模式）。

## 成绩单

| 项 | 改前 | 改后 |
|---|---|---|
| 纯倾诉轮串行 LLM 调用 | 5 次（route + rewrite + toolplan + reply + L1 抽取） | **2 次**（route 合并 + reply；L1 抽取本就异步性质） |
| Kimi 单步超时/5xx 的结果 | 整轮 500（白等最长 2 分钟） | **降级续跑**：路由挂→倾诉轮，工具挂→无工具；仅生成挂才 502 |
| 自伤护栏命中轮 | 先花 120s 生成再整条丢弃 | **前置短路**：0 次 LLM 调用直达干预话术 |
| 可观测性 | 零记录（降级标记无人消费） | 每轮落 `task_runs`（treehole_chat）：状态/延迟/降级 |
| 响应形态 | 整包（文档承诺的流式未实现） | **SSE 流式**（/chat/stream），前端逐段渲染 + 整包回退 |
| 测试 | 15 用例 | **26 用例**（+7 树洞改造 +4 llm 流式解析器），全套 267 通过 |
| 树洞评测 | — | `treehole_eval.py` 26/26 达标（事实保留/检索/护栏/人设四指标无回退） |

## ① 提速：合并 + 短路

- **route + rewrite 合并为一次 JSON 调用**（`ai.treehole_route` 返回 `{"intent","query"}`）：
  原两步各 30s 上限的串行调用合一，prompt 里明确「intent=vent 时 query 给空」
- **倾诉轮结构性跳过工具节点**（`node_tools` 入口判定）：原实现 vent 也要过一次
  tool-plan LLM 问「要不要调工具」——为了决定不做什么的空转，现在直接 `{"tool_results":[],"tools_used":[]}`
- 检索保留：vent 轮用原句做共鸣检索（「你之前也说过…」的来源），只省 LLM 不省检索

## ② 降级链：Kimi 抖动只降级不 500

| 节点 | 失败行为 | 标记 |
|---|---|---|
| ① 路由 | 默认 vent + 原句检索（倾诉是最安全口径） | `ai.mark_degraded()` |
| ③ 工具决策 | 当轮无工具，按已有上下文生成 | `ai.mark_degraded()` |
| ④ 生成 | 如实 502「树洞这会儿走神了」（不能降级——回复就是产品） | task_runs 记 failed |
| caption/压缩/L1 | 原有降级保留（空 caption/旧摘要/跳过抽取） | 原有 |

`send_message` 全程经 `tasks.run_task("treehole_chat", …, retries=0)` 包裹：新增公开
助手 `ai.mark_degraded()` 让服务层兜底也能进降级统计。

## ③ 护栏前置（原⑤生成后检的改造）

- 检查对象本来就是**用户消息**，却在 generate **之后**执行——命中时 120s 的回复已经
  花掉再整条替换。现在挪进 `node_route`：命中即产出干预话术，**条件边直达 writeback**，
  检索/工具/生成整段跳过（测试断言生成 LLM 零调用）
- 词表扩充：强信号补「不想存在/想解脱」（覆盖"我不想存在于这个世界"这类不含原信号的
  否定式存在表达）；夸张缓冲补「困得/尴尬得/无聊得想死」
- 原则不变：护栏仍是**确定性词表**而非模型判断——可解释、可回归的红线不随模型波动

## ④ 可观测性

- 每轮对话落 `task_runs`（treehole_chat：status/started_at/finished_at/degraded）——
  降级标记终于有消费者了；L2 场景聚类的后台刷新也包了 `treehole_l2_refresh`
- 验收用例：`test_chat_records_task_runs`

## ⑤ 流式输出（SSE）

**后端**：
- `llm.chat_messages(on_delta=…)`：OpenAI 线格式流式解析。SSE 增量累积器
  `_StreamAccum` 做成**纯类离线单测**（content 逐段、tool_calls 分片按 index 拼接、
  type 归一 function——BUG-017 的坑在流式路径同样防住）
- 工具轮（$web_search 回声）与流式共存：本轮出现 tool_calls 后的内容（"让我查查"类
  过渡叙述）不外发，回声循环照旧；最终轮内容逐段 on_delta
- 回调经**线程本地槽**（`services/treehole/streaming.py`）传给 generate 节点——函数
  不能进 LangGraph 状态（SqliteSaver 会序列化 checkpoint）
- `POST /api/treehole/chat/stream`：worker 线程跑图，delta 经队列送同步生成器；
  事件序 `delta*→done`（done 带权威整包，前端以此对齐展示与落库）/`error`；
  护栏轮无 delta、done 毫秒级到达

**前端**：`treeholeChatStream`（lib/api.ts，web 专用 fetch 流读取）逐段长到本地气泡；
done 替换为权威全文并挂 citations/tools；**一个 delta 都没收到就挂 → 自动回退整包接口**
（行为与旧版一致）；流到一半断 → 保留半截提示重发（不自动重试，避免重复生成）。

## 追加（同日晚）：query_calories 菜名明细 + 思考程度参数

**⑥ 「我吃了什么」答不上来**：`query_calories` 原来只回 `total_kcal + meals`——菜名明细
在 `calorie_entries.items` JSON 里根本没读。现在：

- summary/data 都带**每餐菜名明细**（`meal_details`：每餐 {kcal, foods}），菜名去重、
  每餐截 8 个/全天截 15 个；纯数字记录（无明细）回退 note
- 支持 `day` 参数（YYYY-MM-DD 白名单校验，默认今天）——「我昨天吃了什么」也接得住
- 工具说明书更新：`query_calories(day?)：查某日（默认今天）热量摄入与吃了什么`

**⑦ 思考程度（用户可调）**：

- 树洞页头新增三档选择器「快/平衡/深思」，随人设卡持久化（`treehole_persona.thinking`
  列，存量库 ALTER 迁移；非法档位 400 白名单拒收；人设 Sheet 保存原样带上不重置）
- 档位映射（`ai.TREEHOLE_THINKING_TO_REASONING`）：快→off（能关思考就关）、平衡→不传参
  （模型默认）、深思→high（k3 的 low/high/max 档）
- 思考参数跨厂商写法抽成共享模块 `ai/reasoning.py`（vision 与 llm 同源，原 vision 私有
  实现改为委托；顺带修了 vision 400 容错漏剥 `thinking_budget` 的小洞）
- `llm.chat_messages(reasoning=…)`：厂商不认思考参数 400 → 剥掉重试一次（BUG-018 手法，
  流式/整包两条路都护住）——k3 在 kimi.com/coding 网关上拒参数也不至于整轮挂

新增测试：菜名明细/去重/day 回退、思考档位全链路（deep→high / fast→off / 非法 400）、
llm 400 剥参重试（真 httpx.Response 构造 400→200）。全套 **270 通过**，eval 26/26。

**⑧ langmem 温度单点化（BUG-024，用户日志报障）**：L1 记忆抽取的 `ChatOpenAI` 写死
`temperature=0`，被 k3（只接受 1）全量 400——对话正常但 **L1 记忆一次都没写进去过**。
温度解析提为公共单点 `llm.resolve_temperature()`，langmem 与 llm 层共用；详见
`BUG记录.md` BUG-024（含 test_config reload 造成双 settings 实例的测试隔离坑）。
