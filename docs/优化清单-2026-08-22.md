## 高价值

1. **user_profiles / pair_relationships 蒸馏表的消费端贫血（2026-08-22 树洞盘点后修正口径）**
   来源：`docs/交接文档-工作流与数据流通.md` §2；本清单早前版本曾写「只写不读（消费者为零）」
   ——**经树洞代码复核该说法不准确**：树洞检索节点与 get_memory_profile 工具经
   `memory/layers.py:account_profile`（layers.py:119-126）已经在读 user_profiles。贫血的
   准确口径是：**pair_relationships 仍零消费**；user_profiles 在**树洞链路已消费**，但
   周报/方案/语录生成路径仍未接入。蒸馏成本与收益仍不匹配，接入剩余消费端或降频。

2. **碎片图片 caption 生产静默失败（BUG-018 遗留，未验证）**
   caption 档默认 high 同样踩思考参数 400 坑，修复靠 400 自愈剥参数重试，但**生产端
   效果从未验证**。建议部署后抽查 `fragments.caption` 近期非空率；一直为空说明图片
   碎片在检索链路里一直是「哑巴」。

3. **BUG-019 遗留：LIKE 双字互含护栏未覆盖**
   「红茶」这类双字查询仍可互含吸到「红茶味饼干/奶茶」行（单字护栏只挡「茶→茶肠」）。
   本轮的饮品先验挡住了联网错值，但**查表方向的双字误吸**仍在。方案候选：互含命中时
   要求长短比 ≥ 某阈值、或互含命中标低置信走 staging 流程。

4. **升级提示只覆盖 source=model 条目**
   `list_calories` 只给 `source=model` 的 item 挂 upgrade；查表/staging 命中的条目即使
   staging 后续来了更准的同名值也不会提示（虽然正式表优先命中时本就不该被 staging
   覆盖，但 staging→staging 更新场景存在）。低频，先记录。

## 中价值

5. **staging (name, brand) 精确匹配脆：改名即断链**
   用户改过菜名后，`staging_id_by_name` 全等匹配查不到 → 不提示、不升级。raw_name
   已落库，可按 raw_name 兜底反查（本轮未做，防震荡改造已铺好数据基础）。

6. **task_runs 表无清理**
   每次管线任务落一行，无限增长。建议 init_db 里挂一个「保留 N 天」的惰性清理。

7. **前端无 toast 体系**
   全项目用 inline 文案 state（adjustNotice/submitError/foodMsg…），一致但弱：操作结果
   不在视野内就看不到。引入轻量 toast（自写 30 行，不引依赖）统一「操作完成/失败」反馈。

8. **SSE 单进程限制**
   `services/events.py` 是进程内总线，多 worker 部署时事件只达同进程订阅者。当前单
   worker 部署无碍；`docs/部署指南.md` 应注明「热量页升级提示依赖单 worker，扩容需换
   Redis pub/sub」。

9. **build chunk > 500kB 警告**
   vite 构建提示主包过大。PWA 首屏可做路由级 dynamic import（React.lazy）拆包。

## 低价值 / 长期

10. **裸 sqlite3 无 ORM**：schema 字符串 + 手写迁移，RENAME 类迁移的坑（BUG-020）已
    踩过一次。项目规模下引 ORM 违反依赖白名单精神，维持现状 + 迁移自查脚本即可。
11. **方案评审团（多 agent fan-out/fan-in）**：README backlog 项，未实现。属于新功能
    而非优化，需单独设计。
12. **grams=0 的识别项不进联网回填**：无分量算不出隐含单价，但联网本可以直接拿
    每 100g 值入库（下次识别有分量即命中）。小改 `missed` 收集条件即可。
