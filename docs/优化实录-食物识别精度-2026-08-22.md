## ① 评测集先行：`scripts/eval_food.py`

**为什么先做这个**：此前所有 prompt/阈值调整都是感觉驱动，没有数字就没有「改好了」的
判据，也无法防回退。树洞侧已有 `treehole_eval.py` 先例，热量侧补齐。

- **匹配层**（默认，离线只读）：30 个种子用例跑 `nutrition.match()`，度量命中率与命中值
  相对误差。参照值全部钉在《中国食物成分表》**真实行**上（米饭→粳米饭(蒸)118、番茄→
  番茄[西红柿]15……），不是拍脑袋
  - `must` 级（19 例）：当前 LIKE 层就应命中的基本盘 + 2 例防误吸（饺子/包子应 miss），
    通过率 <95% 退出码非 0（可挂 CI）
  - `want` 级（11 例）：别名/向量/组合菜的改进目标位，只报告不卡退出
  - 向量层未配置 key 时单列 `vector_err`，不冒充 miss 也不冒充通过
- **端到端**（`--e2e`）：框架就绪——真实拍照走 `recognize_calorie` 全管线，出名字准确率/
  克数 MAE/热量 MAE；照片放 `scripts/eval/foods/`、按 `food_labels.example.json` 格式标注
  （克数用厨房秤称真实值），评测完自动清理产生的记录与临时图
- **历史趋势**：结果追加 `scripts/eval/food_match_history.jsonl`，`--compare` 看每次改动
  的前后对比——以后**改 prompt/匹配必跑**，形成回归纪律

**基线跑出的意外发现**（比数字本身更值钱）：
1. `西红柿` 能命中全靠**厂商数据括号写错**（`奶柿子[西红柿】` 半角开全角关，normalize
   的正则剥不掉才漏过来）——纯运气，不可依赖
2. `土豆/洋芋/红薯` 全 miss：别名在 `[]` 里被 normalize 整体剥掉，LIKE 层永远看不到
3. `小西红柿` 互含吸中单字行 `柿`（74 vs 25，**196% 误差**）：单字护栏只防了查询侧，
   没防候选侧
4. 成分表缺 `饺子/包子/挂面` 整类行（数据覆盖缺口，留给静态补充）

## ② 克数估计：两步推理 prompt + confidence + 用户级偏置

克数是热量误差的最大头（视觉模型裸猜克数是弱项）。

### FOOD_PROMPT 两步推理（`ai/prompts.py`）

把「裸猜克数」改成「**估体积 × 乘密度**」的乘法：

- **第一步（容器参照）**：小饭碗 200ml / 家常碗 300ml / 大汤碗 500ml / 一次性纸杯
  180ml / 玻璃杯 250ml / 马克杯 350ml / 餐盘摊平一层 300ml——先认容器再估食物占比
- **第二步（品类密度）**：熟米饭/面条/粥 0.6 g/ml；水/汤/奶/无糖茶 1.0；肉块/鱼/豆腐
  1.05；叶菜/沙拉 0.3；薯条/膨化 0.15；坚果 0.6；糕点/面包 0.4
  （例：半碗米饭 ≈ 150ml × 0.6 ≈ 90g；一杯牛奶 ≈ 250ml × 1.0 ≈ 250g）

### confidence 字段（模型自报把握度）

- prompt 要求每项输出 0-1 的综合把握度（图清晰/食物常见 ≥0.8，光线差/被遮挡/叫不准
  ≤0.5）；`recognize_calorie` 截断到 [0,1] 后落 `item["confidence"]`，缺失容忍
- 前端待确认卡对 `<0.5` 的项显示「⚠️ 没把握」徽标（title 提示点名字/克数帮忙改）——
  **把稀缺的人工确认引导到最需要的地方**，纠正数据越多校准飞轮越快

### 用户级克数偏置 `_gram_bias`（`services/ledger.py`）

在原有「同类食物纠正样例注入」（帮同类）之上加一层**系统偏置**（帮所有食物）：

- 计算：历史克数纠正里 `用户实际 / 模型估计` 的**中位比值**（最近 30 条）
- 门槛：样本 ≥3；中位偏离 ±50% 以外视为纠正数据本身不可信（用户乱改/单位错），不注入
- 注入：偏置与 1 差 <5% 视为噪声不注入；否则在 calibration 块加一行
  「你历来的分量估计比该用户实际平均偏低约 25%，本次所有克数按 ×1.25 修正」

## ③ 匹配层：别名参与 + 双向护栏 + 做法词表（`services/nutrition.py`）

**零手工别名表**——别名数据本来就在成分表的方括号里，只是被 normalize 扔掉了：

- `_alias_keys()`：提取行名 `[]`（含厂商半角开全角关的破损括号 `[别名】`）里顿号分隔的
  别名，归一去重；圆括号是备注/部位/做法，不算别名
- `_like_rows()`：别名键与主名**同级参与匹配**，别名精确命中同 rank 0——1350 行数据的
  别名全部自动激活（马铃薯[土豆、洋芋] → 土豆/洋芋 都能直接命中），不需要维护同义词字典
- **单字护栏双向化**：查询与候选键**任一**不足两字不做互含扩展——查询侧防「茶→茶肠」
  （BUG-019 原案），候选侧防「小西红柿→柿」（本次新发现，196% 误差）
- 做法词表补 `拍 / 蒜蓉 / 清炖`（拍黄瓜→剥「拍」→按黄瓜计价是合理近似）

## ④ 联网搜索可靠性（追加，同日晚）：源头闸门

**起因**：用户实测日志 `联网值未通过合理性校验，不落共建库：红茶 → 294.0 kcal/100g
（模型参考 4.0）`——饮品先验正确拦截了错值（防御在工作），但联网源**反复返回同一个
坏数据**。追问根因：中文营养库（如薄荷食物库）里「红茶」词条的 294 kcal/100g 指的是
**干茶叶**，数据本身「没错」，错的是**形态口径**——用户喝的是冲泡后液体（1-4
kcal/100ml），旧 prompt 只说「查营养成分（每 100 克可食部分）」，没告诉模型要按
「吃进去的形态」取数，也没要求单位自检（kJ vs kcal）。

修复把可靠性做成**纵深防御**，之前只有第 2、3 层，这次补上第 1 层（源头）：

| 层 | 机制 | 状态 |
|---|---|---|
| 1. 源头（prompt） | 形态口径 + 单位换算 + 交叉自检 + 权威源 + basis 留痕 | **本轮新增** |
| 2. 入库前（sanitize） | 饮品品类先验（>80/150 拒绝）+ kJ 折算 | 已有（BUG-022） |
| 3. 入库后（治理） | 管理面板软删/改值 + SSE 通知 | 已有 |

具体改动：

- **`WEB_SEARCH_FOOD_PROMPT` 重写**：
  - 规则 1【形态必须一致】：按「用户吃进去的形态」给值——冲泡饮品给即饮液体的值，
    **绝不能给干茶叶/咖啡豆/奶粉/浓缩液的值**（prompt 里直接点名红茶 294 这个案例）；
    主食和菜给烹熟/即食状态
  - 规则 2【单位必须是 kcal】：资料是 kJ 的除以 4.184；「每份」换算成每 100
  - 规则 3【交叉自检】：与视觉模型估值对比，差 10 倍以上先怀疑自己搞错形态/单位，
    重新检索（无估值锚点时退化为常识量级自检：「饮品查出三位数 kcal/100」即错）
  - 权威源排序：中国食物成分表 / USDA / 品牌官方标签，多源交叉取代表值
  - 输出新增 `basis` 字段：一句话写清口径（「冲泡后液体每 100ml」），落库日志留痕
- **`web_search_food(name, brand, model_per_100g)`**：
  - `form_hint`：饮品名（与匹配层 `is_drink_name` **同一词表**，延迟导入避免环）注入
    「这是用户喝的饮品，查即饮口径」
  - `ref_hint`：视觉模型隐含单价作为交叉自检锚点写进 prompt——把「入库后拒绝」前移成
    「回答前自纠」，好数据能落库而不是永远被拦
  - 返回值带 `basis`；backfill 落库成功时日志记口径（`联网值入库：红茶 2 kcal/100g
    （冲泡后液体每100ml）`），观测链路闭环
- **测试**：+2（prompt 防呆标记；form_hint/ref_hint 注入断言——脱桩走真身 + 截获
  chat_messages），全套 **256 通过**；smoke 62

**验证方式**（需真实 Kimi 联网，离线测不了）：拍一杯红茶 → 观察日志应从
`未通过合理性校验，不落共建库：红茶 → 294` 变为 `联网值入库：红茶 X kcal/100g
（冲泡后…）`，且 X 应在 0-4 区间；staging 出现红茶活行后，后续识别直接命中不再联网。
