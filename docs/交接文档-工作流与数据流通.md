# 交接文档：工作流、数据流通与记忆层演进方向

> 写给下一位接手者（人或 AI）。本文两条主线：①把当前系统的工作流与数据流讲清楚（读代码前先读这个）；
> ②下一阶段重点——**记忆层改善、数据流通与利用率、多 AI 数据互通、生成效果提升**，这是本文的核心。
> 前置阅读：`docs/技术栈.md`（全栈现状）、`docs/记忆层与关系图设计.md`（产品决策）、`docs/BUG记录.md`（事故复盘与登记格式）。
> 流程约定见 `AGENTS.md`（bug 必须登记、零新依赖、weapp 冻结、测试强制 mock）。

## 0. 系统总览

```
浏览器/PWA（React SPA，src/）
   │  /api JSON（dev 经 vite 代理 :7100 → :8000，生产同源单容器）
   ▼
FastAPI 路由层（server/app/api/）── 同步校验、秒回
   │                                └── 重活全甩 BackgroundTasks / 任务层 tasks.run_task
   ▼
服务层（server/app/services/）── SQLite（WAL 单文件，17 张表，全部业务数据）
   │                              Redis（可选，只放周报生成去重 flag，降级进程内字典）
   ▼
AI 统一接口（server/app/ai/）── 有 key 真实 API / 无 key 确定性 mock / 失败回退记 degraded
   ├── DeepSeek：分类、摘要、画像、周报、方案、追问（全部文本生成）
   ├── 豆包 embedding-vision：图文同空间向量（1024 维）
   ├── 豆包视觉模型（可选）：图片 caption
   └── 高德 Web 服务（可选，AMAP_KEY）：POI / 天气 / 驾车通勤（方案真实数据）
```

核心设计原则（改动时不得违背）：

1. **请求秒回，AI 重活一律后台管线**（碎片管线、愿望向量化、方案生成都是这个模式）
2. **隐私铁律**：隐私碎片/愿望参与一切计算，但永不进任何展示与他人 prompt；过滤永远在服务端
3. **数据单向流**：原始表 → 蒸馏表 → 展示层，展示层不回写原始数据
4. **圈级隔离**：人格、画像、关系、语录、缓存全部按 circle_id 隔离

## 1. 各模块工作流与数据流

### ① 碎片链路（核心写路径）

```
发碎片 → POST /api/fragments 立刻入库返回（processed=0）
       → 后台 pipeline.process_fragment：
         图片 caption（视觉模型，可选）→ DeepSeek 分类（输入=原文+caption）
         → 豆包向量（图文双有取均值归一化）→ 落 fragments.embedding
         → is_knowledge → 抓正文 + 摘要 → knowledge_items（含向量）
         → is_wish → 提取进 wishes（含向量）
       → memory.mark_dirty：作者画像 + 全部用户对打 dirty
```

### ② 记忆层（离线蒸馏）

```
dirty 打点（碎片/愿望/互动写路径）
  → refresh_dirty（每晚 cron 2:40 / 周报生成前强制补跑）：
    四分量（语义 0.35 / 互动 0.30 / 共同愿望 0.20 / 共同主题 0.15）
    → LLM 生成画像 JSON（topics/habit/wish_leaning/summary/style）→ user_profiles
    → LLM 生成关系摘要 → pair_relationships
    逐行提交（写锁毫秒级，见 BUG-001）
读路径：关系图 API 按观看者身份过滤边与主题；周报直接读蒸馏表不现算
```

### ③ 愿望与方案链路

```
加愿望 → 秒回入库（category=do、向量空）→ 后台 process_wish 补分类+向量
匹配   → GET /api/wishes/common：先算池子指纹（id+状态+向量就绪的哈希），
         与 common_wishes_cache 一致直接返回；不一致才现算（聚类+LLM 确认）并回写
方案   → 每晚预生成（无方案的簇逐个 generate_plan）；点击时有缓存秒开，
         无缓存转后台生成 + Web Push 通知 + 前端轮询
         生成链：DeepSeek 抽目的地 → 高德查 POI/天气/通勤 → DeepSeek 写方案
                （价格必标预估 + 跳转链接）→ 存 wishes.plan（含 participants）
追问   → chat_threads/chat_messages（kind='plan'，每人每愿望一条线程）
         上下文 = 愿望 + 方案 + 本周公开语录 + 近 10 条对话
完成   → PUT /api/wishes/{id}/done（可逆）→ 指纹变 → 缓存失效 → 移出匹配池
```

### ④ 周报链路

```
懒触发（首位打开者）/ 有新公开内容滚动刷新 / 手动 generate（force）
  → refresh_dirty 补跑 → _collect_week_data（本周公开碎片 + 语录 ≤8 条 + pair 表连接）
  → resolve_persona（自定义 > 预设 > observer）
  → build_weekly_prompt 组装（人格管语气 + 分寸规则管事实 + 语录 few-shot）
  → DeepSeek → reports 表（UNIQUE(circle_id, week_start)，滚动覆盖）
```

### ⑤ 互动与推送

评论/点赞（仅公开碎片）→ 实时重算用户对互动分量 → 后台 Web Push 给作者（自互动不推）。
方案生成完成、评论、点赞共用 `services/push.py` 的 `_send_to_user`。

### ⑥ 身份与圈子

account（恢复码认领）→ memberships → users（圈内成员）；一切业务数据挂 circle_id + user_id。

## 2. 数据资产清单（★ 利用率审计）

每张表：生产者 → 消费者 → **利用率评级**。这是下一阶段最值得盯的一张表。

| 数据 | 生产者 | 消费者 | 利用率 |
|---|---|---|---|
| fragments（内容/标签/向量/caption） | 碎片管线 | 墙、相关推荐、关系分量、周报、语录 | 高 |
| knowledge_items（摘要/向量） | 碎片管线 | 知识库列表/搜索 | **中**：周报只用 count，摘要与向量没进任何生成上下文 |
| wishes（含向量） | 手动添加 / 碎片提取 | 列表、匹配、方案、分量 | 高 |
| comments / likes | 互动写路径 | 互动分量、语录检索、推送 | 高 |
| **user_profiles.profile（画像 JSON）** | 每晚蒸馏 | **没有消费者（只写不读！）** | **零** |
| └ 其中 style（口头禅/emoji/句长） | 蒸馏（B1） | **没有任何 prompt 使用它** | **零** |
| pair_relationships（四分量/摘要/主题） | 每晚蒸馏 | 关系图、周报 key_connections | **中**：摘要没进方案/追问/画像上下文 |
| 语录（_collect_quotes 实时检索） | 公开碎片+评论 | 周报、方案追问 | **中**：人格化生成只覆盖了这两个场景 |
| wishes.plan（方案 JSON） | 生成/预生成 | 方案卡片、追问 | 高 |
| chat_messages（追问对话） | 用户追问 | 仅回显 | **低**：高价值语料，未回流画像/语录 |
| reports（周报 Markdown） | 周报管线 | 历史列表 | **低**：往期周报内容没有再被检索/引用 |
| task_runs | 任务层 | 排障 | 符合定位 |
| 高德 POI/天气/通勤 | amap.py 实时查询 | 当次方案 | **低**：一次性使用，同城重复愿望重复查询 |

**一句话结论：记忆层现在是"生产端发达、消费端贫血"**——蒸馏管线和数据结构都在，但生成侧（周报/方案/追问/摘要）只吃了一小部分预算好的材料，画像甚至完全没有消费者。

## 3. 下一阶段重点：记忆层与数据流通改善

按 ROI 排序，每条给出落点。前两条是"捡现成的"，强烈建议先做。

### 3.1 统一上下文装配层（最高优先级）

现状：每个生成任务各自手工拼 prompt（`build_weekly_prompt` 是纯函数好底子，但方案/追问/画像都是散装字符串拼接）。建议：

- 在 `ai/` 新增 **context builder**：按任务声明式装配材料块——`persona`（圈人格）、`profiles`（成员画像）、`style`（说话风格）、`pairs`（关系摘要）、`quotes`（语录）、`knowledge`（知识摘要）、`real_data`（高德）等，每块有统一的可见性门禁（公开/当事人/全员）
- 首批收益点（全是"已生产未消费"）：
  - **style 进周报 prompt**：让周报模仿具体成员的语感（现在只有语录原句，没有风格抽象）
  - **画像 summary/topics 进方案与追问**：方案知道"这两人的共同主题"，追问能引用
  - **pair 摘要进周报 AI 洞察段**：现在只有 key_connections 列表
  - **knowledge 摘要进周报知识沉淀段**（现在只有 count）
- 铁律不变：装配层的每块材料必须过可见性门禁（设计文档 §5），隐私内容永不进 prompt

### 3.2 数据回流闭环（记忆层的"记忆"真正长出来）

- **追问对话回流**：`chat_messages` 是成员最主动的表达场景，纳入画像摘录来源（`memory.py` 的 excerpts 查询加一路 chat_messages，注意只取本人发言）与语录检索
- **完成信号变关系信号**：愿望勾选 done（共同完成）现在是纯剔除；共同完成的愿望应当**增强**两人关系分量（共同愿望分量的"兑现"维度），这是比"都想"更强的信号
- **方案反馈**：方案被追问/被采纳（无追问且直接勾 done ≈ 采纳）可作为方案质量信号落库，供 prompt 迭代评估

### 3.3 召回增强（突破"本周"窗口）

- 周报/方案目前只用**本周**数据；向量检索已是毫秒级，可按主题召回**历史**碎片/知识（比如"最近三个月大家反复提起的"），周报深度会上一档
- 往期周报正文向量化入检索池，新周报可引用"上周提到的事后来怎么样了"——连续性是最能感受到"记忆"的体验

### 3.4 多 AI 互通现状与方向

现状已是单向流水线且有一处好示范（视觉 caption → 参与分类打标签）。缺口：

- **embedding ↔ LLM 没有反馈环**：LLM 抽取的主题/tag 没有回写用于改进聚类（共同主题目前只精确匹配 tag 字符串，同义不同词就漏）。方向：蒸馏时让 LLM 对高频 tag 做归并，归并表落库
- **高德数据无沉淀**：同城 POI 查询结果可按（city, keywords）缓存进 SQLite，重复愿望直接复用
- **结构化中间表示**：各 AI 输出目前直接进 prompt 字符串；context builder 落地后，材料块统一为结构化 dict，最后一步才渲染成文本——评估与缓存都好做

### 3.5 生成质量评估基线

prompt 迭代目前没有回归手段（mock 桩只保确定性不保质量）。建议建 golden cases：

- 固定若干输入材料（ fragments/语录/画像样本），存 `server/tests/fixtures/`
- 每次改 prompt，用真实 key 跑一遍 golden 输入，输出存档对比（人工评或 LLM 互评）
- 不进 CI（CI 保持 mock 确定性），作为发版前手动闸：`scripts/eval_prompts.py`

## 4. 硬约束（改动时不得违反）

1. **零新依赖**（pip/npm 都不许加）；中文注释匹配周边密度；最小 diff
2. `weapp/` 冻结一行不动；`src/core/` 双端共享，改动必须 `cd weapp && npx tsc --noEmit` 通过
3. 测试强制 mock 模式（env 覆盖 key）；隐私铁律见 §0.2
4. embedding 换维度/模型后必须跑 `scripts/reembed.py`（BUG-002）
5. 写事务绝不跨 LLM 调用（BUG-001）；新 AI 写接口默认秒回 + 后台管线（BUG-003）
6. 每个 bug 修复后按格式补登 `docs/BUG记录.md`
